§1 Problem

为什么需要质量门禁？

痛点规范写在文档里，但没人执行；测试覆盖率 7%，代码裸奔上线

🏗️ 建筑类比
想象你是一个建筑工地的安全主管。工地上有安全规范手册，但没人检查工人是否戴安全帽。

没有门禁的做法：规范写了"必须戴安全帽"，但工人嫌热不戴，主管假装没看见。直到出了事故才追责——但已经晚了。

有门禁的做法：工地入口装了闸机，不戴安全帽的人根本进不去。不是靠自觉，是靠硬件。

质量门禁就是代码仓库的闸机。

没有门禁的痛

CLAUDE.md 写了"组件必须有测试"，但 15 个组件只有 1 个有测试（7%）。规范形同虚设，坏代码畅通无阻。

三层门禁

本地脚本 → Git Hook → CI 检查，三层拦截。测试文件不存在？提交不了。类型检查不过？编辑时就知道。

结果

覆盖率从 7% 到 100%。不是靠人记住"要写测试"，而是不写测试就提交不了。

前端组件匹配规则

扫描 frontend/src/components/*.tsx，排除 *.test.tsx 和 index.tsx。每个组件必须有同目录下的 ComponentName.test.tsx。

后端路由匹配规则

扫描 backend/app/routers/*.py，排除 __init__.py。每个路由文件必须有 backend/tests/integration/test_{name}.py。

§4 PostToolUse Hooks

即时类型诊断：写完就知道对不对

实时每次编辑文件后，自动运行对应语言的类型检查——不用等 commit

语言触发文件检查工具耗时检查内容
TypeScript*.ts / *.tsxtsc --noEmit~2-3s类型错误、接口不匹配、未使用的导入
Python*.pymypy~3-5s类型注解错误、函数签名不匹配
Rust*.rscargo check~3-10s借用检查、类型错误、未使用的变量
.claude/hooks/post-edit-check.sh — 运行逻辑
# 1. 从 stdin 读取 hook JSON，提取 file_path FILE_PATH=$(echo "$INPUT" | python3 -c "extract file_path") # 2. 跳过非源码路径 case "$FILE_PATH" in *node_modules*|*.venv*|*__pycache__*|*target/*) exit 0 ;; esac # 3. 按扩展名分发 case "$REL_PATH" in *.ts|*.tsx) cd frontend && npx tsc --noEmit ;; *.py) uv run mypy "$REL_PATH" ;; *.rs) cd src-tauri && cargo check ;; esac # 4. 非阻塞：失败仅 warning，不阻塞编辑 || true # exit 0 always
⚡ 非阻塞设计
类型检查失败时，hook 只输出警告（exit 0），不阻塞编辑操作。这是因为类型错误通常是渐进式的——你可能正在写一半的代码，中间状态有类型错误是正常的。

真正的阻塞发生在提交时（lefthook pre-commit）和合并时（CI 门禁）。PostToolUse hook 的价值是即时反馈，不是强制执行。
§5 Browser Verification

Playwright MCP：让 AI 打开浏览器验证

视觉代码改完了，让 Claude 打开浏览器实际看看效果——不是盲写盲测

Playwright MCP 是什么

微软官方的 MCP 服务器，让 Claude 能控制浏览器：导航页面、点击元素、截图验证、检查 DOM 状态。比人工打开浏览器快 10 倍。

用在哪

前端组件改完后，让 Claude 打开页面截图验证布局；API 改完后，让 Claude 调用接口验证响应。不是"我觉得改对了"，而是"我看到了改对了"。

.mcp.json — 项目级 MCP 配置
{ "mcpServers": { "playwright": { "command": "npx", "args": ["@playwright/mcp@latest", "--headless"] } } }
§6 Git Hooks

Lefthook：提交时自动拦截 + 自动修复

拦截pre-commit hook 跑测试文件检查 + 自动 lint:fix

lefthook.yml
pre-commit: parallel: true commands: test-file-gate: run: bash scripts/check-test-coverage.sh frontend-lint-fix: glob: "frontend/src/**/*.{ts,tsx}" run: cd frontend && npm run lint:fix && git add -u frontend/src/ stage_fixed: true

test-file-gate

运行检查脚本，验证所有组件和路由都有对应测试文件。缺失任何一个，提交直接被拦截。

frontend-lint-fix

当 staged 文件包含 *.ts / *.tsx 时，自动运行 lint:fix 并重新 stage 修复后的文件。格式问题自动修复，不用手动调。

§7 CI Gates

GitHub Actions：最后的防线

合并PR 必须通过所有检查才能合并——不允许"先合并后补测"

CI Job检查内容命令
test-file-gate所有组件/路由的测试文件存在性bash scripts/check-test-coverage.sh
frontend-lint-and-unitESLint 检查 + Vitest 单元测试npm run lint && npm run test -- --run
backend-unit后端业务逻辑单元测试pytest backend/tests/unit -v
backend-api-integrationAPI 路由集成测试pytest backend/tests/integration -v
python-baseline仓库基线测试 + 评估测试pytest tests/ -v && pytest evals/ -v
🚫 不允许的例外
规则很简单：任一 Job 失败，PR 禁止合并。没有"先合并后补测"，没有"这个 warning 以后再修"。

如果 CI 红了，要么修代码，要么修测试。不接受第三个选项。
§8 Skeleton Tests

骨架测试：最小成本达到 100% 覆盖

务实不要求每个测试都有 10 个 case，但每个组件/路由至少有一个骨架

前端骨架测试（Vitest）

最小标准：渲染不报错 + 关键交互 + 一个边界。用 vi.mock mock API 层，避免真实网络请求。15 个组件，36 个测试用例。

后端骨架测试（pytest）

最小标准：1 条 2xx 成功路径 + 1 条 4xx/5xx 失败路径。用 httpx.AsyncClient + ASGITransport 直接测 FastAPI app。7 个路由，21 个测试用例。

前端骨架测试示例 — BrainstormStreamBubble.test.tsx
import { render, screen } from '@testing-library/react'; import BrainstormStreamBubble from './BrainstormStreamBubble'; describe('BrainstormStreamBubble', () => { it('renders agent name', () => { render(<BrainstormStreamBubble agentName="TestAgent" />); expect(screen.getByText('TestAgent')).toBeInTheDocument(); }); it('renders streaming content when provided', () => { render(<BrainstormStreamBubble agentName="Agent" streamingContent="Hello" />); expect(screen.getByText('Hello')).toBeInTheDocument(); }); it('renders without content when streamingContent is empty', () => { const { container } = render(<BrainstormStreamBubble agentName="Agent" />); expect(container.querySelector('.chat-message')).toBeInTheDocument(); }); });

§10 Trade-offs

代价与收益

诚实质量门禁不是免费的——有收益，也有成本

收益
  • 坏代码提交不了 — 测试文件不存在就拦截，不是靠自觉
  • 即时反馈 — PostToolUse hook 让你写完就知道类型对不对，不用等 commit
  • 覆盖率从 7% 到 100% — 骨架测试成本低，但保证每个模块都有最低保障
  • 三语言统一 — TypeScript、Python、Rust 用同一套门禁逻辑
  • CI 自动化 — PR 必须通过所有检查，不允许"先合并后补测"
  • lint 自动修复 — lefthook pre-commit 自动跑 lint:fix，格式问题不用手动调
代价
  • 每次编辑多 2-10 秒 — PostToolUse hook 运行类型检查，拖慢交互节奏
  • 骨架测试不等于有效测试 — "渲染不报错"是最弱的测试，不能替代业务逻辑测试
  • 维护成本 — 新增组件/路由必须同步新增测试，否则提交不了
  • cargo check 首次慢 — Rust 编译首次需要 10-30s，有缓存后 ~3s
  • hook 配置复杂度 — 三层防御 + MCP 配置，新成员需要理解整体架构
  • 存量代码补齐 — 从 7% 到 100% 需要一次性补齐所有缺失的测试
§11 Pitfalls

常见反模式

避坑知道不该做什么，和知道该做什么一样重要

❌ 反模式为什么不好✅ 正确做法
骨架测试写完就不管了 "渲染不报错"是最弱的测试，不能发现业务逻辑 bug 骨架是起点，逐步补充交互和边界测试
hook 失败就阻塞 写一半的代码中间状态有类型错误是正常的，阻塞会打断心流 PostToolUse 非阻塞（warning），commit/CI 才阻塞
只加 CI 不加本地检查 开发者 push 后才发现问题，反馈循环太长 三层都要有：本地 → hook → CI
测试文件放错目录 检查脚本找不到测试文件，误报"缺失" 前端同目录 *.test.tsx，后端 tests/integration/
跳过存量补齐 门禁只能管增量，存量裸奔的代码永远不会被检查到 一次性补齐所有缺失的骨架测试
PostToolUse 跑完整测试套件 每次编辑跑 36 个测试要 10 秒+，严重影响交互体验 PostToolUse 只跑类型检查，完整测试留给 commit/CI
