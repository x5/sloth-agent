Agent Eval

如何给 AI Agent 打分？
不是靠直觉，不是靠感觉——
而是让它跑真实任务，用四维评分模型量化能力

自动化评估 四维评分 三级难度 回归测试
§1 Motivation

为什么需要 Eval？

一句话你改了一行代码，怎么知道 Agent 变强了还是变弱了？

🎯 考试类比
想象你是一个老师。你教了一个学生（Agent）写代码。每次你改进教学方法（改代码），你都想知道学生有没有进步。

最靠谱的方法是什么？——考试。出一套标准化的试卷（eval tasks），让学生做，打分，记录成绩。下次改进教学后再考一次，对比分数。

这就是 Eval 框架做的事：给 Agent 出题、监考、打分、记录成绩。

回归测试

改了代码后，Agent 的能力有没有退化？跑一遍 eval 就知道。就像软件的单元测试，但测的是 Agent 的"智能"。

能力基线

每次大版本跑一次 eval，记录分数。时间长了就能看到 Agent 的成长曲线：v0.5 得 72 分，v0.6 得 85 分。

可量化决策

"我觉得 Agent 变强了"不够。需要数字：正确率多少？产出质量如何？效率怎样？用数据驱动开发决策。

§2 Task

什么是 Eval Task？

人话翻译一道考题 = 一份 Plan + 一组期望结果

每个 Eval Task 就是一道"考试题"。我们给 Agent 一份 Plan（比如"创建一个 CRUD API"），让它跑完整个开发流水线，然后检查它的产出是否符合预期。

evals/tasks.yaml — 任务定义
eval_tasks: - name: crud-api description: Create a REST CRUD API difficulty: 1 # 难度等级 L1 plan: evals/plans/crud-api.md expected: gate1_pass: true # lint + type check 通过 gate2_pass: true # test + coverage 通过 min_files: 4 # 至少生成 4 个文件 min_coverage: 0.80 # 测试覆盖率 ≥ 80% lint_errors: 0 # 零 lint 错误 max_tokens: 50000 # token 消耗上限 max_retries: 3 # 最多重试 3 次
📝 考试类比
Task = 一道考题
Plan = 题目要求（"请实现一个 CRUD API"）
Expected = 评分标准（"代码能编译、测试通过、覆盖率 80%"）
Agent 跑流水线 = 学生答题
Scoring = 老师批改打分
§3 Levels

三级难度：L1 / L2 / L3

类比小学卷、中考卷、高考卷——难度不同，考的能力也不同

不是所有任务都一样难。写一个简单脚本和搭建一个全栈应用，难度天差地别。我们用三个等级来区分，每个等级对应不同的流水线深度和评分权重。

等级考什么流水线深度典型任务
L1基础编码能力：能写对代码Builder → Gate1（lint/type）写脚本、CLI 工具、单个函数
L2工程能力：代码质量 + 测试Builder → Reviewer → Gate2（test/coverage）API 服务、数据处理管道
L3全栈能力：从开发到部署完整流水线 + Gate3（smoke test）前后端应用 + 部署配置
§4 Scoring

四维评分模型

核心不是单一分数，而是四个角度综合评判——就像高考不只看一科

每个 Task 的总分归一化到 100 分。但不是笼统地给一个总分，而是从四个维度分别打分，加权汇总。这样你能清楚地看到 Agent 到底强在哪、弱在哪。

正确性 (40%)

最核心的指标。Agent 写的代码能不能通过 Gate？L1 只需过 Gate1，L2 需过 Gate1+Gate2，L3 全部三道 Gate。通过越多，分数越高。

公式：40 × (通过 Gate 数 / 该等级最大 Gate 数)

产出质量 (30%)

代码写得怎么样？三个子项各占 1/3：生成的文件数是否达标、测试覆盖率是否达标、lint 错误是否为零。每个子项独立计分。

过程效率 (20%)

Agent 完成任务"花了多少力气"？三个指标：token 消耗、重试次数、耗时。没超上限 = 满分，超了按比例扣分。高效完成 = 高分。

部署产物 (10%)

仅 L3 任务计分。检查 Dockerfile 和 docker-compose.yml 是否存在且可解析。L1/L2 不计此项，权重均摊到其他三维。

🎓 高考类比
正确性 = 主科（语数英），占比最大，决定基本盘
产出质量 = 理综/文综，考察综合能力
过程效率 = 答题速度，同样分数用时更短 = 更强
部署产物 = 加分项（竞赛获奖），只有特定考试才有

L1/L2 没有"加分项"，所以 10% 的部署权重被均摊到其他三项：44.4% / 33.3% / 22.2%
§5 Grades

等级标准：A / B / C / D

一眼看懂不是冰冷的数字，而是直观的等级

A
90+ 分 全部 Gate 通过，产出质量高，效率好
B
75+ 分 核心 Gate 通过，有小瑕疵
C
60+ 分 基本能跑通，但有明显问题
D
<60 分 流水线未跑通或产出质量差

§7 CLI

命令行接口

使用一条命令跑评估，一条命令看报告

Terminal
# 跑全部 task $ sloth eval run # 只跑 L1 难度的任务 $ sloth eval run --level 1 # 跑单个 task $ sloth eval run --task crud-api # 查看某次评估结果 $ sloth eval report v0.6.0 # 对比两个版本的成绩 $ sloth eval compare v0.5.0 v0.6.0
📊 版本对比类比
sloth eval compare v0.5.0 v0.6.0 就像看两个学期的成绩单对比：

v0.5.0 平均分 72 → v0.6.0 平均分 85 → Agent 进步了 13 分
其中正确性从 35→40（满分），效率从 12→18（有提升空间）

这就是数据驱动的开发决策：改了什么让正确性满分了？效率为什么还没跟上？
§8 Architecture

文件结构

实现eval 框架的代码组织

evals/ 目录结构
evals/ ├── tasks.yaml # 任务索引 — 所有考题的元数据 ├── plans/ # 每个 task 的 Plan 文件（题目） │ ├── crud-api.md │ ├── fix-type-error.md │ └── add-tests.md ├── runner.py # 执行引擎 — 跑流水线 + 采集指标 ├── scoring.py # 评分模块 — 四维度加权打分 ├── models.py # 数据模型 — EvalTask, EvalResult └── results/ # 评测结果（按版本存储 JSON） ├── v0.5.0.json └── v0.6.0.json

设计灵感

GAIA（通用 AI 助手评估）— 难度分级、真实任务的设计理念

SWE-bench（软件工程基准）— 自动验证、可复现的评估方法

关键约束

只在大版本时运行（使用真实 LLM，有成本）

不真正部署，只检查部署产物（Dockerfile 等）

结果按版本号存储，支持跨版本对比
