SLOTH AGENT · DELTA SPEC
2026-05-02 · Workflow Methodology

Delta Spec

先改文档，再改代码
每次需求变更，不是直接动手写代码——
而是先写一份变更说明书（Delta），再按单据施工

Spec 是源头真相 改代码前先改 Spec 一次变更 = 一个目录 完成即归档
§1 Problem

为什么不能直接改代码？

痛点代码改了，文档没跟上；三个月后没人知道当时为什么这样改

🏗️ 建筑类比
想象你是一个建筑工地的工头。业主说"我要加一个阳台"。

错误做法：直接让工人开始砌砖。三个月后物业来查图纸，发现图纸上没有这个阳台。业主要改回去了，你也不记得当时阳台的承重是怎么算的。

正确做法：先在施工图纸上标注变更（画一个 Delta），业主签字确认，然后工人按图施工。图纸始终反映建筑的真实状态。

Delta Spec 就是这个施工图纸的变更单。

没有 Delta 的痛

代码改了三版，文档还是第一版。新人来了看不懂代码为什么这样写。回滚时发现需求文档和代码完全对不上。

Delta 带来什么

每次变更都有迹可循：为什么改（proposal）、改了什么（delta）、怎么实现的（tasks）。代码和文档永远同步。

Spec = 唯一真相

代码和文档冲突时，以 Spec 为准。Spec 不是"写完就扔"的文档，而是活的系统描述，跟着代码一起演进。

§2 Principles

三条铁律

记住这三条规则是整个工作流的基础

铁律一：Spec 是源头真相

docs/specs/<module>/spec.md 描述系统的当前真实状态，不是愿景、不是计划、不是愿望清单。它反映的是"系统现在是什么样"。

铁律二：改代码前先改 Spec

任何需求变更，必须先写成 Delta，再动手改代码。不是"改完代码补文档"，而是"先写变更单，再按单施工"。

铁律三：一次变更 = 一个目录

每次变更在 docs/changes/ 下创建独立目录，包含 proposal、delta、tasks 三个文件。完成后整个目录归档。

§3 Flow

六步标准流程

全景从需求到归档，六步走完一个变更的完整生命周期

§4 Documents

三份关键文档

核心proposal 说"为什么"，delta 说"改什么"，tasks 说"怎么做"

Proposal

proposal.md

# 变更提案: Eval 框架重新设计 > 日期: 2026-05-02 > 影响模块: specs/eval/spec.md ## 动机 当前 eval 只有骨架，无法 真正评测 Agent 能力。 需要参考 GAIA 和 SWE-bench 建立完整评测体系。 ## 范围 - 重新设计 eval runner - 引入四维度评分模型 - 支持 L1/L2/L3 分级 - 不改数据库模型 - 不改现有 Gate 接口
Delta

delta.md

# Delta: Eval 框架重新设计 > 关联模块: specs/eval/spec.md ## ADDED + REQ-EVAL-001: Runner 复用 Sloth 流水线执行真实任务 + REQ-EVAL-003: 四维度评分 正确性/质量/效率/部署 ## MODIFIED ~ REQ-旧-001: runner 从"只验证 文件存在"改为"执行流水线" ## REMOVED - REQ-旧-003: 移除 smoke_test 功能合并到 Gate3
Tasks

tasks.md

# 实现任务 ## Phase 1: 基础结构 - [x] 创建 models.py - [x] 迁移 tasks.yaml - [ ] 创建 results/ 目录 ## Phase 2: 核心引擎 - [ ] 实现 scoring.py - [ ] 重写 runner.py - [ ] HookManager 指标采集 ## Phase 3: CLI - [ ] sloth eval run - [ ] sloth eval report - [ ] sloth eval compare
📋 三份文档的关系
proposal.md = 装修申请单（为什么装、装哪里、不装哪里）
delta.md = 施工变更单（加什么、改什么、拆什么，用条款编号）
tasks.md = 施工进度表（具体每一步做什么，做完打勾）

三份文档分工明确：proposal 给决策者看，delta 给 Spec 维护者看，tasks 给施工者看。

§6 Scale

什么时候需要 Plan？

决策树小改动用 Delta 够了，大功能才需要 Plan

变更规模流程示例
小改动Delta → tasks.md → 实现 → 归档修复 bug、加一个小功能、改配置
中改动Delta → tasks.md → 实现 → 归档跨 2-3 个模块的功能改进
大功能Delta → Plan → tasks.md → 实现 → 归档MVP 桌面应用（9 个 Iter）、新子系统
📐 什么时候画施工图
换个灯泡（小改动）：口头说一声就干了 → 只需要 Delta
装修厨房（中改动）：需要施工单 → Delta + tasks 够了
盖一栋楼（大功能）：需要完整施工图 → Delta + Plan + tasks

Plan 保留在 docs/plans/，是独立的项目管理文档，适合跨多迭代的大功能追踪。小变更的 tasks.md 直接写在 Delta 目录里就够了。
§7 Merge

Delta 如何合并到 Spec？

关键步骤完成实现后，把变更条款"写入"源头真相

追加到 spec 对应章节 在"已实现"节末尾添加新条目 spec.md 末尾追加 → MODIFIED 修改条款 → 替换 spec 中对应内容 找到原条款，用新内容覆盖 原条款 → 新条款 REMOVED 删除条款 → 从 spec 中移除 找到原条款，整段删除 原条款 → 删除 实际操作示例 ADDED REQ-EVAL-003 → 在 spec.md 的"核心设计"节末尾追加评分模型描述 MODIFIED REQ-旧-001 → 找到 spec.md 中 runner 描述，替换为新内容
§8 Trade-offs

优缺点分析

诚实没有银弹——Delta Spec 有明显优势，也有明确代价

优势
  • 文档永远同步 — 代码改了文档必须跟着改，不会出现"文档过时"的问题
  • 变更可追溯 — 每次变更有 proposal（为什么）、delta（改什么）、tasks（怎么做），三个月后还能查到
  • 需求先于实现 — 强制先想清楚"改什么"再动手，减少返工
  • 新人友好 — 读 spec.md 就能了解系统当前状态，不用翻 git log
  • 回滚有据 — archive 里保存了每次变更的完整快照，回滚时知道改了什么
  • AI 友好 — 结构化的 delta 格式让 AI Agent 也能理解和执行变更流程
代价
  • 前期开销 — 改一行代码也要先写 proposal + delta + tasks，小改动感觉繁琐
  • 维护负担 — Spec 需要持续维护，如果不认真更新反而成为误导
  • 学习曲线 — 团队需要理解 ADDED/MODIFIED/REMOVED 格式和合并规则
  • 不适合快速原型 — 探索阶段代码变化太快，Delta 跟不上节奏
  • Spec 膨胀 — 长期累积后 spec.md 可能变得很长，需要定期精简
  • 合并冲突 — 多人同时修改同一模块的 spec 可能产生文档合并冲突
§9 Pitfalls

常见反模式

避坑知道不该做什么，和知道该做什么一样重要

❌ 反模式为什么不好✅ 正确做法
改完代码再补 Delta Delta 变成了"事后文档"，需求和实现可能已经对不上了 先写 Delta，再改代码
Delta 里写实现细节 Delta 描述"改什么需求"，不是"怎么实现"。实现细节属于 tasks.md Delta 只写需求条款，tasks 写实现步骤
跳过 proposal 直接写 delta 没有动机和范围的 delta 是无根之木，读者不知道为什么这样改 三份文档都要写
完成不归档 changes/ 目录堆积未完成的变更，无法区分进行中和已完成 完成后立即移到 archive/
Spec 不更新 Delta 写了但没合并到 spec，spec 和代码脱节 实现完成后立即合并 delta 到 spec
跨 Plan 搬运内容 维护两份同样的内容必有一份过期，产生矛盾 引用 Spec 章节，不跨 Plan 引用
§10 Structure

文档目录结构

全貌Spec 是圆心，Delta 是过程，Archive 是历史

docs/ 完整目录结构
docs/ ├── specs/ # 源头真相 — 系统的当前状态 │ ├── architecture/spec.md │ ├── eval/spec.md │ ├── brainstorm/spec.md │ └── ...22 个模块 │ ├── changes/ # 进行中的 Delta 变更 │ ├── README.md # 格式说明 │ └── eval-framework-redesign/ │ ├── proposal.md # 为什么 │ ├── delta.md # 改什么 │ └── tasks.md # 怎么做 │ ├── archive/ # 历史归档 — 完成的变更 │ ├── initial-specs/ # 初始 Spec 快照 │ ├── brainstorm-fluid-discussion/ │ └── message-queue/ │ ├── plans/ # 大功能的实施计划（跨多迭代） ├── qa/ # 验证清单 ├── design/ # 设计文档 └── articles/ # 方法论文章（本文档）

Spec 是源头，代码是 Spec 的实现。如果代码和 Spec 不一致，是代码错了，不是 Spec 错了。

Closing

好的变更管理，不是写更多文档，而是让每一份文档都有存在的理由。

记住proposal 说为什么，delta 说改什么，tasks 说怎么做——三份文档，一个都不能少
