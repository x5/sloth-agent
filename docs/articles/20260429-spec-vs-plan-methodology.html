Spec vs Plan

需求与实现的分层方法论
Spec 回答 What & Why · Plan 回答 How & When
双层文档驱动，让 AI 和人都知道做到哪了、下一步做什么

What & Why How & When Single Source of Truth v1.0
§1 Definition

什么是 Spec？什么是 Plan？

一句话Spec = 盖什么房子；Plan = 施工图纸和工序

维度Spec（规格文档）Plan（实施计划）
回答什么问题What & Why — 做什么、为什么How & When — 怎么做、何时做
读者PM、决策者、新加入的开发者执行开发的工程师
稳定性高 — 功能需求不轻易变低 — 随实现进展频繁更新
生命周期长期存在，归档后仍可回溯实施完成后冻结，不再更新
内容粒度功能列表 + 验收标准具体任务 + 文件路径 + 代码模式
语言业务语言，不涉及技术细节技术语言，含具体实现方案
§2 Rationale

为什么需要两层文档？

人话翻译没人会把户型图和施工图画在同一张纸上

分离关注点

Spec 和 Plan 的读者不同。PM 不需要知道 main.py:42 改了什么，开发者不需要在功能需求里翻找实现任务。

稳定 vs 易变

功能需求稳定（"用户能创建项目"），实现细节频繁变化。分开就不会因为改了方案而破坏需求文档。

可回溯

一个 Spec 对应多个 Plan（Iter-1→Iter-4）。Spec 始终一致，Plan 各自独立，方便以后了解"当初怎么实现的"。

单一真相源

Spec 是源头，Plan 由 Spec 生成。两者冲突以 Spec 为准。禁止跨 Plan 搬运内容而不回归 Spec。

§3 Workflow

Spec → Plan → Execute 完整工作流

铁律需求变了先改 Spec，方案变了只改 Plan

先改 Spec，再改 Plan 方案变了 → 只改 Plan，不改 Spec 冲突 → Spec 为准，Plan 纠正 跨 Plan 引用 → 引用 Spec 章节
§4 Templates

Spec 文档模板

要点功能需求 + 验收标准 + 不做什么 = 完整 Spec

Spec

docs/specs/YYYYMMDD-feature-slug-spec.md

# [产品/功能名称] 规格 > 关联架构: `docs/design/xxx.md` > Figma 设计: `fileKey` node `nodeId` > 日期: YYYY-MM-DD > 状态: DRAFT | IN PROGRESS | DONE ## 1. 产品概述 [一段话说明这个产品/功能是什么，给谁用，解决什么问题] **原则：** [核心设计原则] ## 2. 技术栈 | 层 | 技术 | ## 3. 功能需求 ### 3.1 功能模块 A（迭代 X） | 功能 | 描述 | API | | 创建 | [描述] | `POST /api/xxx` | ## 4. UI 结构 [布局图或线框图] ## 5. 数据模型 字段名: 类型 (约束) — 说明 ## 6. 迭代规划 ### 迭代 1: [名称]（N 天） **目标/交付物/验收标准** ## 7. 错误处理 - [场景] → [处理方式] ## 8. 不做什么 - 不实现 XXX（延至迭代 N） ## 9. 项目结构（目标） *Spec 版本: X.X — YYYY-MM-DD*
1
功能需求用表格

功能名、描述、API 端点三列清晰，一眼看懂范围

2
验收标准用 checkbox

每个迭代下的验收项必须是可验证的、非歧义的

3
"不做什么"是硬约束

比"做什么"同样重要，防止范围蔓延

4
数据模型要完整

字段名、类型、约束、说明缺一不可

5
版本号 + 变更日志

每次修改 Spec 都要更新版本号和变更摘要

6
状态标记

DRAFT → IN PROGRESS → DONE，让读者一眼知道当前阶段

§5 Templates

Plan 文档模板

要点任务 + 文件路径 + 实现要点 + 验证步骤 = 可执行的 Plan

Plan

docs/plans/YYYYMMDD-feature-slug-plan.md

# [产品/功能名称] 实施计划 > 对应 Spec: `docs/specs/xxx.md` > 日期: YYYY-MM-DD > 版本: X.X ## 0. 总览 | 迭代 | 内容 | 状态 | | Iter-1 | 功能A | ✅ DONE | | Iter-2 | 功能B | 🚧 IN PROGRESS | ## N. Iter-N: [名称]（N 天） ### 目标 [一句话说清本轮交付什么] ### Task N.1: [任务名称] **状态：** ✅ | 🚧 | ⬜ **描述：** [任务要做什么] **文件：** - `path/to/file1.tsx` — [修改内容] **实现要点：** - [关键实现细节 1] **验证：** - [ ] [验证步骤] *Plan 版本: X.X — YYYY-MM-DD*
1
每个 Task 标注状态

✅ DONE / 🚧 IN PROGRESS / ⬜ TODO，一眼看懂进度

2
文件路径必须精确

path/to/file.tsx:42 级别，不是目录级别

3
实现要点写关键决策

不是"写一个函数"，而是"复用 X 模式，参数用 Y 结构"

4
验证步骤要可执行

不是"测试通过"，而是具体的 curl 命令和预期响应

5
Plan 可以推翻重写

Plan 是消耗品，发现更好的方案就更新，不用保留历史

6
关联 Spec 链接

Plan 文件头部必须引用对应的 Spec 文件路径

§6 Architecture

文档体系全景图

结构Spec 是圆心，Plan 是半径，QA 是终点

spec.md plans/ YYYYMMDD-slug-plan.md design/ topic-architecture.md qa/ iter-N-verification.html articles/ YYYYMMDD-topic.md
§7 Pitfalls

常见反模式

避坑知道不该做什么，和知道该做什么一样重要

❌ 反模式为什么不好✅ 正确做法
没有 Spec 直接写 Plan 不知道要做成什么样就开始拆任务，方向大概率偏 先写 Spec 对齐需求
Plan 里写功能需求 Plan 应该只有实现任务，需求归属 Spec 需求变更先改 Spec
Spec 里写文件路径 Spec 是给 PM 看的，文件路径是开发者的事 文件路径只放在 Plan 里
多个 Plan 互相搬运内容 维护两份同样的内容必有一份过期 引用 Spec 章节，不跨 Plan 引用
Spec 完工后不再更新 需求澄清是持续过程，Spec 要跟着演进 每次变更更新版本号 + 变更日志
Plan 的状态不更新 别人不知道做到哪了 每个 Task 标注 ✅/🚧/⬜
