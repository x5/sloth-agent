# Spec vs Plan — 需求与实现的分层方法论

> 如何在 Sloth Agent 项目中用 Spec + Plan 双层文档驱动开发

---

## 1. 什么是 Spec？什么是 Plan？

| 维度 | Spec（规格文档） | Plan（实施计划） |
|------|-----------------|-----------------|
| **回答什么问题** | What & Why（做什么、为什么） | How & When（怎么做、何时做） |
| **读者** | PM、决策者、新加入的开发者 | 执行开发的工程师 |
| **稳定性** | 高——功能需求不轻易变 | 低——随实现进展频繁更新 |
| **生命周期** | 长期存在，归档后仍可回溯 | 实施完成后即冻结，不再更新 |
| **内容粒度** | 功能列表 + 验收标准 | 具体任务 + 文件路径 + 代码模式 |
| **语言** | 业务语言，不涉及技术细节 | 技术语言，含具体实现方案 |

**一句话总结：**

- **Spec** = 这是我们要建造的东西，以及为什么这样建造
- **Plan** = 这是我们建造它的步骤，每一步怎么做

---

## 2. 为什么需要两层文档？

### 2.1 分离关注点

Spec 和 Plan 的读者不同。PM 不需要知道 `main.py` 第 42 行改了什么，开发者不需要在功能需求里翻找实现任务。

### 2.2 稳定 vs 易变

Spec 定义的功能需求相对稳定（"用户能创建 Inspiration"）。Plan 中的实现细节频繁变化（文件路径、代码模式、任务拆分方式）。把两者分开，就不会因为改了实现方案而破坏需求文档。

### 2.3 可回溯

一个 Spec 可能对应多个 Plan（例如迭代 1 的 Plan、迭代 2 的 Plan）。Spec 始终保持一致，Plan 各自独立，方便以后了解"这个功能当初是怎么实现的"。

### 2.4 单一真相源

**Spec 是源头，Plan 由 Spec 生成。** 如果 Spec 和 Plan 出现矛盾，以 Spec 为准。禁止在多个 Plan 之间直接搬运内容而不回归 Spec。

### Spec 编写标准

1. **功能需求用表格**：功能名、描述、API 端点三列清晰
2. **验收标准用 checkbox**：每个迭代下的验收项必须是可验证的、非歧义的
3. **"不做什么"是硬约束**：比"做什么"同样重要，防止范围蔓延
4. **数据模型要完整**：字段名、类型、约束、说明缺一不可
5. **版本号 + 变更日志**：每次修改 Spec 都要更新版本号和变更摘要
6. **状态标记**：DRAFT → IN PROGRESS → DONE，让读者一眼知道当前阶段

```markdown
# [产品/功能名称] 实施计划

> 对应 Spec: `docs/specs/xxx.md`
> 日期: YYYY-MM-DD
> 版本: X.X

---

## 0. 总览

| 迭代 | 内容 | 状态 |
|------|------|------|
| Iter-1 | [功能模块 A] | ✅ DONE |
| Iter-2 | [功能模块 B] | 🚧 IN PROGRESS |
| Iter-3 | [功能模块 C] | ⬜ TODO |

**关联 Spec：** `docs/specs/xxx.md`

---

## N. Iter-N: [迭代名称]（N 天）

### 目标

[一句话说清本轮交付什么]

### Task N.1: [任务名称]

**状态：** ✅ | 🚧 | ⬜

**描述：** [任务要做什么]

**文件：**
- `path/to/file1.tsx` — [修改内容]
- `path/to/file2.py` — [修改内容]

**实现要点：**
- [关键实现细节 1]
- [关键实现细节 2]

**验证：**
- [ ] [验证步骤]

### Task N.2: [任务名称]

[同上结构]

---

*Plan 版本: X.X — YYYY-MM-DD*
*变更: [本次变更摘要]*
```

### Plan 编写标准

1. **每个 Task 标注状态**：✅ DONE / 🚧 IN PROGRESS / ⬜ TODO，一眼看懂进度
2. **文件路径必须精确**：`path/to/file.tsx:42` 级别，不是目录级别
3. **实现要点写关键决策**：不是"写一个函数"，而是"复现 X 模式，参数用 Y 结构"
4. **验证步骤要可执行**：不是"测试通过"，而是"`curl -X POST /api/xxx -d '{...}'` 返回 200"
5. **Plan 可以推翻重写**：Plan 是消耗品，发现更好的方案就更新，不用保留历史
6. **关联 Spec 链接**：Plan 文件头部必须引用对应的 Spec 文件路径

## 5. 两者如何配合使用

### 5.1 工作流

```
需求澄清
  ↓
编写/更新 Spec（先回答 What & Why）
  ↓
Spec 确认（与 PM/团队对齐）
  ↓
编写 Plan（从 Spec 拆解 How & When）
  ↓
Plan 确认（开发者评审实现方案）
  ↓
按 Plan 执行（创建 TODO → 逐个 Task 实现）
  ↓
每完成一个 Iter，更新 Plan 状态 + Spec（如有需求变更）
  ↓
全部完成 → Spec 标记 DONE，Plan 冻结
```

### 5.2 变更管理

- **需求变了** → 先改 Spec，再改 Plan
- **实现方案变了** → 只改 Plan，不改 Spec
- **Spec 和 Plan 冲突** → Spec 为准，Plan 纠正
- **跨 Plan 引用** → 引用 Spec 章节，禁止 Plan 之间互相搬运内容

### 5.3 文档命名规范

```
docs/
├── specs/
│   └── YYYYMMDD-<feature-slug>-spec.md    # 规格文档
├── plans/
│   └── YYYYMMDD-<feature-slug>-plan.md    # 实施计划
├── design/
│   └── <topic>-architecture.md            # 架构设计
├── qa/
│   └── iter-N-verification.html           # QA 验证清单
├── ref/
│   └── <source-doc>.md                    # 参考资料
├── guides/
│   └── YYYYMMDD-<topic>-guide.md          # 使用指南
└── articles/
    └── YYYYMMDD-<topic>.md                # 方法论/博客文章
```

## 6. 常见反模式

| 反模式 | 为什么不好 | 正确做法 |
|--------|-----------|---------|
| 没有 Spec 直接写 Plan | 不知道要做成什么样就开始拆任务，方向大概率偏 | 先写 Spec 对齐需求 |
| Plan 里写功能需求 | Plan 应该只有实现任务，需求归属 Spec | 需求变更先改 Spec |
| Spec 里写文件路径 | Spec 是给 PM 看的，文件路径是开发者的事 | 文件路径只放在 Plan 里 |
| 多个 Plan 互相搬运内容 | 维护两份同样的内容必有一份过期 | 引用 Spec 章节，不跨 Plan 引用 |
| Spec 完工后不再更新 | 需求澄清是持续过程，Spec 要跟着演进 | 每次变更更新版本号 + 变更日志 |
| Plan 的状态不更新 | 别人不知道做到哪了 | 每个 Task 标注 ✅/🚧/⬜ |
