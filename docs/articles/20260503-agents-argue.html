§1 What is an Agent

到底什么是 Agent？

基础Agent = 角色 + 记忆 + 工具 + 行动——像一个有专长的同事

🏢 公司会议类比
想象你是一家公司的 CEO，面临一个战略决策。你可以自己一个人想，也可以叫上 CTO、CFO、COO 一起开会。

一个人想的问题：你只能看到自己专业领域内的东西。你是技术出身，可能忽略了财务风险；你是市场出身，可能低估了技术难度。单一视角，必然有盲区。

团队开会的好处：CTO 说"这个技术上可行但需要 3 个月"，CFO 说"3 个月的 burn rate 我们扛不住"，COO 说"可以先做 MVP，6 周上线，边跑边迭代"。不同视角碰撞，才能逼近最优解。

一个 Agent 就是这样一个有专长的数字同事——它有明确的角色定位、专业领域和思考方式。

角色（Role）

每个 Agent 有一个明确的角色定义——"你是资深后端架构师"、"你是前端性能优化专家"。这个角色决定了它的思考框架和表达方式。

上下文（Context）

Agent 能看到完整的对话历史——谁说了什么、什么时候说的。它不是凭空发言，而是基于前面的讨论做出反应。

行动（Action）

Agent 不只是说话，还能调用工具——读写文件、执行代码、搜索信息。讨论不仅仅是"嘴炮"，还能落地执行。

§2 Why Multi-Agent

为什么需要多个 Agent 一起讨论？

动机单一视角有盲区，多角度碰撞才能发现"你不知道你不知道什么"

单 Agent 的局限

即使用最长的 system prompt，一个 Agent 也只能有一套思维框架。它可能在自己不擅长的领域自信地给出错误答案——而且没人纠正它。

多 Agent 协作的优势

不同的 Agent 有不同的知识边界和思维模式。当架构师提出一个方案，安全专家会指出漏洞，产品经理会质疑用户体验——这种碰撞是单人思考无法模拟的。

A1
后端架构师
建议用微服务架构拆分——每个服务独立部署，扩展性好。
A2
安全专家
"建议用微服务架构拆分"
我不同意。微服务之间通信会增加攻击面。如果你们坚持走这条路，至少要先做服务间 mTLS，每个服务独立鉴权。
A3
产品经理
两位说的都对。但我们只有 4 周时间。同意安全专家的 mTLS 方案，但建议先只拆 2 个核心服务，其余保持单体——渐进式拆分。
§3 Architecture

怎么让 Agents 吵起来？

核心顺序发言 → 完整上下文 → 多轮迭代 → 自然收敛——不是群聊，是圆桌会议

顺序发言

Agent 不是并行发言（那会导致各说各话），而是一个接一个。后面的人能看到前面所有人的发言，产生真正的"对话感"。

多轮迭代

不是一轮就结束。每轮结束后，下一轮重新开始——直到所有人无话可说（PASS）或达到最大轮数（8 轮）。

自然收敛

不设固定轮数。当所有 Agent 在某一轮都选择沉默时，讨论自然结束——就像真实会议中大家达成共识后的安静。

§4 Streaming

SSE 流式传输：一字一字"现场直播"

实时Server-Sent Events 让每个 Agent 的思考过程逐字呈现，不是等它想完再一次性贴出来

SSE 事件类型触发时机携带数据前端行为
agent_startAgent 开始生成回复agent_id, agent_name, agent_number创建流式气泡，显示头像和名字
agent_tokenLLM 每输出一个 tokentoken 文本片段追加到气泡内容，光标闪烁
message_doneAgent 发言完成并存入数据库完整内容、message_id、round锁定气泡，显示完整消息
agent_passAgent 回复 "PASS"agent_id, agent_name跳过该 Agent，不显示气泡
discussion_end所有轮次结束总消息数、总轮数显示结束分隔线
user_message用户消息写入数据库确认message_id, content替换临时 ID 为真实 ID
heartbeat空闲 30 秒无保持连接存活，无 UI 变化
SSE 数据流示例 — 一个 Agent 的完整发言过程
event: agent_start data: {"agent_id":"a1","agent_name":"后端架构师","agent_number":1} event: agent_token data: {"token":"我"} event: agent_token data: {"token":"建议"} event: agent_token data: {"token":"采用"} event: agent_token data: {"token":"渐进式"} event: agent_token data: {"token":"拆分"} ... event: message_done data: {"agent_id":"a1","message_id":"msg_abc","full_content":"我建议采用渐进式拆分...","round":2}
📺 直播 vs 录播
SSE 的价值在于即时性。如果等 Agent 全部想完再一次性显示，用户要盯着空白屏幕 10-30 秒——体验极差。

逐字流式输出就像看直播：你知道 Agent 正在"思考"，能看到它的思维过程逐步展开。这种渐进式信息披露让等待变得可以接受，甚至有趣。
§5 Convergence

冷却计时器：让讨论自然收敛

精巧不是靠固定轮数结束，而是用一个两阶段状态机判断"大家是不是真的没话说了"

两阶段确认的意义

为什么不是"全部 PASS → 立即结束"？因为 Agent 生成回复需要时间（5-30 秒）。如果 Agent 2 在 Agent 1 发言期间恰好处于"无话可说"状态，直接结束会误杀正在生成的回复。

冷却期给了一个缓冲窗口——"等一下，万一有人在打字呢"。

为什么需要 CONFIRMING？

单次冷却可能不够。COOLING_DOWN 阶段如果又有新发言，立刻回到 RUNNING。只有连续两段沉默（冷却期 + 确认期都无人发言），才判定讨论真正结束。

这就像会议主持人问"还有人有补充吗？"——等 3 秒，再问一次——没人吭声，散会。

§6 UI

聊天界面如何呈现多 Agent 讨论？

交互流式气泡、线程颜色、引用预览、队列管理——不只是"聊天"，是"会议直播"

BrainstormStreamBubble

实时流式气泡组件。Agent 发言时显示编号头像、名字、逐字增长的内容、闪烁光标。无内容时显示思考动画（三个跳动的点）。

引用预览

当 Agent 回复某条特定消息时，气泡上方显示被引用内容的彩色边框预览——像邮件客户端的引用折叠。

消息队列

系统忙时（Agent 正在发言），用户消息进入队列。角标显示排队数量，队列中的消息逐个处理，每处理完一个触发一轮新讨论。

🎨 线程着色：让对话关系一目了然
多轮讨论中，消息之间形成复杂的引用关系（A 回复 B，C 回复 A 的回复……）。为了让用户能视觉追踪讨论脉络，每条引用链使用 FNV-1a 哈希算法为根消息生成一个确定性颜色。

同一条讨论线内的所有消息使用同一个色系（蓝、青、绿、紫 6 色调色板），不同讨论线用不同颜色。用户扫一眼就能看出"这几条消息在讨论同一个话题"。
§7 Connection

持久连接：一个连接撑起整场会议

架构不是每次发言都新建连接——一个 SSE 连接持续到会议结束，心跳保活

旧方案：One-Shot SSE

每条用户消息创建一个新的 SSE 连接，Agent 说完就断开。问题：连接建立有开销（HTTP 握手、数据库连接池获取），频繁建连断连浪费资源。

新方案：Persistent Connection

一个 SSE 连接从会话开始持续到结束。用户消息通过 POST /inject 注入（返回 202 立即释放），后端通过 asyncio.Queue 接收并触发 Agent 轮次。心跳事件每 30 秒发送，防止代理层超时断连。

§8 Control

中断机制：用户可以随时"闭嘴"

控制权两级中断——静音当前发言 vs 结束整个讨论——用户始终握有控制权

abort_round（静音当前轮）

用户点击"闭嘴"按钮，中断当前正在发言的 Agent。本轮其余 Agent 跳过，直接进入下一轮或收敛判断。不会结束整个会话，用户可以继续发消息。

abort（结束会话）

用户关闭头脑风暴模式时触发。中断所有 Agent，关闭持久连接，清理状态。在数据库中写入一条"会话结束"的系统消息，保留完整讨论记录。

中断实现：asyncio.Queue 哨兵模式
# abort() 被调用时，向队列注入一条空消息作为"哨兵" async def abort(self): self._abort = True await self.message_queue.put("") # 唤醒阻塞在 queue.get() 的协程 # 引擎主循环检测到哨兵后立即退出 msg = await asyncio.wait_for(queue.get(), timeout=30) if self._abort: break # 退出 while 循环，结束 SSE 流

§10 Trade-offs

代价与收益

诚实多 Agent 讨论不是魔法——有显著的收益，也有不可忽视的成本

收益
  • 多视角碰撞 — 架构师、安全专家、产品经理从各自领域提出观点，发现单一视角遗漏的盲区
  • 自然收敛机制 — 不是硬编码"讨论 3 轮"，而是让对话自然走向共识或分歧
  • 实时流式体验 — SSE 逐字传输，用户能看到 Agent "正在思考"，而不是干等 30 秒
  • 持久连接架构 — 一个连接撑起整场会议，避免频繁建连断连的开销
  • 线程着色 — FNV-1a 哈希为每条讨论线生成确定性颜色，视觉上追踪对话脉络
  • 用户始终握有控制权 — 两级中断机制，可以静音当前发言或结束整个讨论
代价
  • 响应延迟 — 3 个 Agent × 每轮 10-30 秒 = 一轮讨论 30-90 秒。多轮可能数分钟
  • Token 消耗巨大 — 每个 Agent 的上下文包含完整对话历史，3 个 Agent × 8 轮 = 大量 token
  • 可能陷入循环 — Agent 之间可能来回重复相同论点，需要冷却计时器强制收敛
  • 连接管理复杂 — 持久 SSE 连接 + 心跳 + 优雅断开 + 断线重连，比普通 HTTP 请求复杂得多
  • 前端状态管理 — 流式 token 拼接、临时 ID 替换、消息队列、中断处理——Store 逻辑量大
  • 不是所有场景都适用 — 简单问答用多 Agent 讨论是杀鸡用牛刀，反而拖慢体验
§11 Pitfalls

常见反模式

避坑知道不该做什么，和知道该做什么一样重要

❌ 反模式为什么不好✅ 正确做法
Agent 并行发言 各说各的，看不到别人的观点，失去"对话"的意义 顺序发言，后面的 Agent 能看到前面所有人的内容
固定轮数结束 讨论可能已经无话可说还在强行继续，或者关键共识还没达成就被截断 冷却计时器 + PASS 机制，让讨论自然收敛
每次发消息新建 SSE 连接 HTTP 握手开销、数据库连接池压力、代理层重连延迟 持久连接 + inject 端点，一个连接全生命周期
所有 Agent 用同一个 system prompt 同质化输出，三个 Agent 说一样的话——浪费 token 每个 Agent 有独立角色定义和思维框架
前端不做消息队列 用户在 Agent 发言期间连续发消息，导致状态混乱 队列缓冲，逐个处理，显示排队计数
心跳间隔太短 每次心跳唤醒事件循环，增加空闲时的 CPU 开销 30 秒心跳，平衡保活需求和资源消耗
